# 분류 점검 판단 기준

기록물 제목은 평균 28자다. 제목만으로 알 수 있는 것과 알 수 없는 것을 구분하는 것이 이 기준의 중심이다. 제목으로 확정할 수 없는 것을 확정한 것처럼 적으면 뒤 단계가 그 결과를 사실로 다룬다.

## 묶음 파일 읽는 법

`batches/{batch_id}.json`의 구성은 다음과 같다.

| 항목 | 내용 |
| --- | --- |
| `부서명`, `부서대응` | 문서를 등록한 부서와, 그 부서에 적용하는 분류기준표 부서. 유형이 `준용`이면 같은 기능의 다른 부서 기준표를 빌려 쓴 것이고, `승계추정`이면 폐지된 부서를 현 부서로 추정 연결한 것이다 |
| `부서후보` | 그 부서의 단위업무(`unit_id`, U로 시작)와 소속 기록물철(`file_id`, F로 시작). `참고`는 기록물철명이 확정되지 않은 항목의 설명이며 철 단위로는 고를 수 없다 |
| `부서공통후보` | 어느 부서에나 있는 서무·복무·회계 등 공통 업무(`common_id`, C로 시작) |
| `items[].추가후보` | 제목과 글자 구성이 비슷한 다른 부서의 기록물철. 글자만 비슷하고 업무가 다른 경우가 많다 |

## 1. 독립 판단 (blind-classifier)

제목마다 아래 순서로 수준을 정한다.

1. **철**: 제목의 업무가 `부서후보`의 기록물철 하나의 이름·설명에 들어맞는다.
2. **단위업무**: 단위업무는 분명한데 그 안의 기록물철 가운데 하나로 좁힐 수 없다. 둘 이상의 철에 걸치거나 `참고`만 있는 단위업무가 여기에 해당한다.
3. **부서공통**: 휴가, 출장, 지출결의, 사무용품, 보안점검처럼 부서 고유 업무가 아닌 공통 업무다. 부서후보에도 같은 업무가 있으면 부서후보를 고른다. 그 부서가 주관하는 업무이기 때문이다.
4. **추가후보의 철·단위업무**: 다른 부서 소관이 분명할 때만 고른다. 등록 부서가 그 업무를 하지 않는다는 근거가 제목이나 수신·발신처에 있어야 한다.
5. **미배정**: 맞는 후보가 없다(`분류기준표에 해당 업무 없음`), 제목이 '보고', '알림', '테스트'처럼 업무를 알 수 없다(`제목 정보 부족`), 그 밖의 사유(`기타`).

판단할 때 다음을 지킨다.

- 접수 문서는 보낸 기관의 업무가 아니라 받은 부서가 그 문서로 처리할 업무를 기준으로 본다. 전 부서에 뿌린 안내(사규 개정 알림, 근무 기준 알림 등)는 받은 부서의 고유 업무가 아니므로 부서공통의 대내문서·복무·서무 항목에서 찾고, 없으면 미배정으로 둔다.
- 제목의 괄호 안(용역 이름, 대상 공항, 업체 이름)이 업무 대상을 알려 주는 경우가 많다. '계약체결 알림(○○ 용역)'은 계약 절차가 아니라 ○○ 용역이 속한 업무로 볼 수 있는지 먼저 따지고, 판단이 서지 않으면 계약 절차 쪽 후보와 견주어 확신도를 낮춘다.
- 낱말이 겹친다는 이유만으로 고르지 않는다. 기록물철 설명에 적힌 업무 활동과 제목의 활동이 같은지 본다.

확신도는 `높음`(제목의 핵심어가 후보의 이름·설명과 같은 업무를 가리키고 경쟁 후보가 없음), `보통`(업무는 맞아 보이나 경쟁 후보가 하나 있음), `낮음`(추정에 가깝거나 경쟁 후보가 여럿)으로 적는다.

결과 파일 `results/{batch_id}.json`:

```json
{"batch_id": "batch_0001", "results": [
  {"key": "k001", "level": "철", "id": "F0201", "confidence": "높음", "reason": "전자감사시스템 기능 개선 요청은 '전자감사시스템 운영·개선' 철의 설명과 같은 활동"},
  {"key": "k002", "level": "미배정", "id": null, "confidence": "낮음", "unassigned_type": "제목 정보 부족", "reason": "제목이 '자료 제출'뿐이라 업무를 알 수 없음"}
]}
```

`level`은 `철`·`단위업무`·`부서공통`·`미배정`, `id`는 각각 F·U·C로 시작하는 ID 또는 null이다. 모든 key를 한 번씩 적는다.

## 2. 판정 (label-judge)

`compare/{batch_id}.json`에서 `판정필요`가 true인 항목만 다룬다. 항목에는 제목, `기존분류`(구분, 단위업무명, 소기능, 그 단위업무의 기록물철 이름), `의심신호`, `독립판단`, `비교`가 들어 있다.

| verdict | 기준 |
| --- | --- |
| `기존 타당` | 제목의 업무가 기존 단위업무(철이면 그 철)의 범위에 들어간다. 독립 판단 쪽이 더 구체적일 뿐 기존 분류가 틀린 것은 아닌 경우도 여기에 넣는다 |
| `오류` | 제목의 업무가 기존 분류의 범위 밖이고, 묶음 후보 가운데 범위에 들어맞는 다른 항목이 있다. 그 항목을 정정안(`level`, `id`)으로 적는다 |
| `판단불가` | 제목만으로 어느 쪽인지 정할 수 없다. 기존 분류가 범위 밖으로 보이지만 맞는 정정안이 후보에 없을 때도 여기에 넣고 reason에 그 사실을 적는다 |

- 정정안은 독립 판단과 달라도 된다. 독립 판단이 틀렸다고 보면 다른 후보를 고른다. 정정안의 수준은 `철`·`단위업무`·`부서공통` 가운데 하나다.
- `비교`가 '철 차이'이면 단위업무는 같다. 기존 철과 독립 판단의 철 가운데 제목에 맞는 쪽을 고르되, 둘 다 가능하면 `기존 타당`으로 둔다.
- `비교`가 '독립 판단 미배정'이면 독립 판단 근거를 읽고 기존 분류를 직접 평가한다.
- 의심신호 S3(소관 외)은 다른 부서의 단위업무에 들어갔다는 뜻이다. 부서 대응이 `준용`·`승계추정`이면 대응표 자체가 추정이므로 S3만으로 오류라고 하지 않는다.
- 의심신호 S1(분류 불일치)은 같은 유형의 제목이 여러 단위업무에 나뉘었다는 뜻이다. 같은 key의 항목들을 함께 보고, 한 곳이 맞으면 나머지를 그쪽으로 정정하는 안을 낸다. 문서 수가 많은 쪽이 맞다고 단정하지 않는다.

결과 파일 `judge/{batch_id}.json`:

```json
{"batch_id": "batch_0001", "verdicts": [
  {"item": "k003-1", "verdict": "오류", "level": "단위업무", "id": "U0310", "reason": "제목은 출입증 발급 승인인데 기존 분류는 ESG·사회공헌관리로 범위 밖. 출입증관리 단위업무의 설명과 일치"},
  {"item": "k004-2", "verdict": "기존 타당", "reason": "월차결산 보고는 회계결산·내부통제 범위"}
]}
```

## 3. 반박 검증 (correction-challenger)

판정이 `오류`인 항목마다 기존 분류를 지지할 근거를 찾는다. 다음 질문에 차례로 답한다.

1. 기존 단위업무의 소기능·소속 기록물철 이름과 설명 가운데 제목의 업무를 담을 수 있는 것이 있는가?
2. 판정 근거가 낱말의 겹침에만 기대고 있지 않은가? 정정안의 설명에 적힌 활동이 제목의 활동과 실제로 같은가?
3. 제목이 여러 업무로 읽힐 수 있는데 판정이 한쪽만 고려하지 않았는가?
4. 정정안이 다른 부서 항목이면, 등록 부서가 그 업무를 하지 않는다는 근거가 있는가?

| result | 기준 |
| --- | --- |
| `반박 실패` | 기존 분류로는 제목을 설명할 수 없고 정정안이 맞다. 이 건만 정정 권고가 된다 |
| `반박 성공` | 기존 분류로 제목을 설명할 수 있거나, 정정안이 기존 분류보다 낫다고 할 근거가 없다 |
| `판단불가` | 기존 분류는 틀려 보이지만 정정안도 맞는지 확신할 수 없다 |

확신이 서지 않으면 `반박 실패`로 적지 않는다. 정정 권고는 사람이 그대로 반영할 수 있어야 하기 때문이다.

결과 파일 `challenge/{batch_id}.json`:

```json
{"batch_id": "batch_0001", "challenges": [
  {"item": "k003-1", "result": "반박 실패", "reason": "ESG·사회공헌관리의 기록물철 어디에도 출입증 업무가 없고 정정안의 설명은 정규출입증 발급 승인을 명시"}
]}
```

## 공통

- reason은 한두 문장으로, 제목의 어느 표현이 후보의 어느 설명과 맞거나 맞지 않는지 적는다. '적절함', '관련 있음'만 적지 않는다.
- 결과 파일을 쓴 뒤 `validate_batch.py`로 검사한다. 검사는 대상 항목이 빠짐없이 있는지, ID가 묶음 후보에 있는지, 정정안이 기존 분류와 다른지를 본다.
