# 단위업무 기준 조직 설계 방법

## 왜 단위업무를 기준으로 삼는가

부서 이름은 개편할 때마다 바뀌지만 단위업무는 공사가 실제로 하는 일의 단위라 개편 전후에도 남는다. 대안을 "어느 단위업무를 어느 부서에 두는가"로 적으면 세 가지를 얻는다. 개편 범위를 단위업무 수와 기록물철 수로 셀 수 있고, 개편 뒤 분류기준표를 고칠 대상이 바로 나오며, 서로 다른 대안을 같은 단위로 비교할 수 있다. 그래서 이 하네스의 모든 조치는 `unit_id` 목록으로 표현한다.

## 자료와 한계

`data/facts/`의 파일은 `build_facts.py`가 계산한 값이며 줄마다 근거 ID가 있다.

| 파일 | 근거 ID | 내용 | 알아 둘 한계 |
| --- | --- | --- | --- |
| `01_부서현황.md` | `DP-` | 분류기준표 부서별 단위업무·기록물철·기능 수 | 분류기준표에 항목이 적은 부서(ESG경영실 2건 등)는 업무가 적은 것이 아니라 기준표 작성이 덜 된 것일 수 있다 |
| `02_기능분산.md` | `DS-U`, `DS-S`, `DS-M` | 같은 단위업무명·소기능·중기능이 여러 부서에 있는 경우 | 이름이 같아도 대상 시설이나 지역이 다르면 다른 업무다 |
| `03_유사단위업무.md` | `SM-` | 다른 부서의 비슷한 단위업무 쌍 | 글자 구성의 유사도다. 내용이 같다는 판정이 아니다 |
| `04_문서량.md` | `VL-` | 부서별·연도별 문서 수와 점유율 | 2021·2026년은 수록 범위가 달라 보인다. 연도 비교는 점유율로 한다. 단위업무별 문서 수는 없다 |
| `05_수발신.md` | `CM-` | 부서 간 수신·발신 문서 수 | 발신처가 "한국공항공사 사장"인 문서가 빠져 실제보다 적다. 상대 비교에만 쓴다 |
| `단위업무목록.md` | 없음 | 단위업무 703개 목록 | 기록물철명·설명은 `../kac-shared/data/classification.json`에서 찾는다 |

문서목록의 부서명(김포운영단, 제주시설단 등)은 분류기준표의 부서명과 다르다. 제주·김해의 운영단·시설단과 대부분의 지방 공항은 분류기준표에 항목이 없어 김포공항·청주공항 항목을 빌려 쓴다(`04_문서량.md`의 "분류기준표 대응" 열). 이런 부서에 대한 조치는 "분류기준표상 모델 부서의 단위업무를 기준으로 했다"고 전제에 적는다.

## 근거 인용 규칙

수치를 근거 없이 쓰면 경영진이 검증할 수 없는 주장이 보고서에 실린다. 그래서 수치는 다음 두 형식으로만 쓴다.

- Markdown(진단서, 검토서, 보고서): `[근거ID 항목=값]`. 예: `[DP-001 단위업무 수=76]`. 값을 쓰지 않고 출처만 가리킬 때는 `[SM-D01]`.
- 대안 JSON: 조치의 `근거` 배열에 `{"fact_id": "SM-D01", "항목": "쌍 수", "값": 73}`.

항목 이름은 `facts.json`의 `값`에 있는 이름과 글자까지 같아야 한다. `check_option.py`와 `check_citations.py`가 값을 대조한다. 사실 자료에 없는 수치(인원, 예산, 처리 시간)는 쓰지 않고 "자료 없음"이라고 적는다.

## 진단

대안은 진단서의 문제를 바탕으로 만든다. 문제를 다음 순서로 찾는다.

1. **같은 기능이 여러 부서에 있는 곳**: `02_기능분산.md`에서 부서 수가 많은 단위업무명·소기능, `03_유사단위업무.md`에서 쌍 수가 많은 부서 조합. 각 쌍의 기록물철명·설명을 열어 실제로 같은 일인지, 대상(시설·지역)만 다른 같은 종류의 일인지, 이름만 비슷한 다른 일인지 구분해 적는다.
2. **한 부서에 성격이 다른 기능이 모인 곳**: `01_부서현황.md`에서 중기능 수가 많은 부서레벨(2). 중기능 목록을 보고 서로 관련이 적은 기능이 섞였는지 본다.
3. **부서 크기의 불균형**: 단위업무·기록물철 수와 문서량이 부서 사이에 크게 다른 곳. 분류기준표 미비 때문인지 실제 업무량 차이인지 구분한다.
4. **문서 왕래가 많은 부서 조합**: `05_수발신.md`에서 문서 수가 많은 쌍. 서로 다른 본부·실에 속하면서 왕래가 많으면 기능 배치를 다시 볼 후보다.
5. **전략 방향 관련 단위업무의 위치**: 전략 방향이 있으면 관련 단위업무를 `단위업무목록.md`에서 검색해 어느 부서들에 흩어져 있는지 적는다.

문제마다 `ISSUE-01` 형식의 ID, 관련 unit_id, 근거 표기, 자료의 한계, 관련 관점을 적는다. 5~10건으로 추린다. 대안은 쓰지 않는다.

## 대안 설계

### 절차

1. 진단서에서 자기 관점과 관련된 문제를 고른다. 관점별 지침은 `references/perspectives.md`에 있다.
2. 문제마다 관련 단위업무의 기록물철명과 설명을 `classification.json`에서 읽는다. 이 확인 없이 이름만으로 묶으면 대상 시설이 다른 업무를 합치는 오류가 난다.
3. 조치를 정한다. 조치 유형은 다섯 가지다.

   | 유형 | 뜻 | `대상부서` |
   | --- | --- | --- |
   | 이관 | 단위업무를 기존의 다른 부서로 옮긴다 | 분류기준표에 있는 부서 |
   | 통합 | 여러 부서의 같은 종류 단위업무를 기존 부서 한 곳으로 모은다 | 분류기준표에 있는 부서 |
   | 신설 | 새 부서를 만들어 단위업무를 모은다 | 분류기준표에 없는 새 이름 |
   | 분리 | 한 부서의 단위업무 일부를 떼어 다른 부서나 새 부서로 보낸다 | 받는 부서 |
   | 폐지검토 | 단위업무 자체의 존속을 검토한다 | 없음 |

4. 조치마다 이유와 근거를 적는다. 이유에는 "왜 이 단위업무들이 한 부서에 있어야(또는 떨어져야) 하는가"를 업무 내용으로 설명한다.
5. `02_constraints.md`의 제약과 관계있는 조치는 `규정검토`에 적는다. 법률·정관이 정한 기능을 없애는 조치, 독립성이 필요한 기구를 다른 부서 아래로 넣는 조치는 만들지 않는다.
6. 기대효과, 위험, 전제·확인필요를 적는다. 위험에는 이 대안으로 나빠질 수 있는 것을 구체적으로 적는다(예: 현장 공항에 남아야 할 시설 점검 업무가 본사로 올라가 대응이 늦어질 수 있음).
7. `check_option.py --write`를 실행해 통과시킨다.

### 대안 JSON 형식

`assets/option_example.json`이 통과하는 예시다. 항목은 다음과 같다.

| 항목 | 내용 |
| --- | --- |
| `option_id` | 프롬프트에서 받은 값(`OPT-A`, `OPT-B`, `OPT-C`) |
| `관점` | `기능통합`, `전략사업`, `현장운영` |
| `대안명` | 경영진이 내용을 짐작할 수 있는 이름 |
| `전략방향` | 사용자가 준 문장 그대로. 없으면 "지정 없음" |
| `요약` | 3~5문장 |
| `조치` | 배열. 조치마다 `조치명`, `유형`, `unit_ids`, `대상부서{부서1, 부서2}`, `이유`, `근거[{fact_id, 항목, 값}]`, 관련 `issue_ids` |
| `기대효과`, `위험`, `전제·확인필요` | 문장 배열 |
| `규정검토` | `[{제약ID, 판단(저촉 없음/절차 필요/저촉 우려), 설명}]` |
| `영향규모` | `check_option.py --write`가 채운다. 직접 쓰지 않는다 |
| `검토반영` | 보완할 때만. 지적별로 반영 내용이나 반영하지 않은 이유 |

한 단위업무는 한 조치에만 넣는다. 부서 전체를 옮기는 조치도 그 부서의 unit_id를 모두 나열한다. 그래야 영향 규모가 계산된다.

### 좋은 대안의 조건

- 조치 3~8건. 각 조치가 진단서의 문제와 연결된다.
- 조치의 대상이 unit_id로 특정되고 근거값이 사실 자료와 일치한다.
- 옮기지 않기로 한 것도 적는다. 이름은 같지만 지역·시설이 달라 그대로 두는 단위업무가 있으면 `전제·확인필요`에 이유를 적는다. 검토자가 누락으로 보지 않게 하기 위해서다.
- 효과를 수치로 약속하지 않는다. 자료에 인원·비용이 없으므로 "중복 작성이 줄어든다"처럼 방향만 적고 규모는 영향규모 항목에 맡긴다.
